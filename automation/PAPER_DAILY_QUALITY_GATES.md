# 论文日报质量门禁

本文件把正式日报实际采用的检索、全文复核、内容编写、图片检查和网站发布流程固化为强制门禁。
自动化必须同时遵守 `PAPER_DAILY_AUTOMATION.md`、`Paper_Reader.template.txt` 与
`paper-daily/config.yaml`；若表述存在差异，采用更严格且不编造信息的一项。

## 1. 当期产物合同

一次正常发布至少产生并相互对应的以下产物：

- 合并去重后的窗口候选池：`paper-daily/data/processed/RUN_DATE_window_candidates.json`。
- 内部评分与全文复核记录：`paper-daily/data/processed/RUN_DATE_scored.json`。
- 保留检索、评分、排除原因和运行信息的本地日报：`paper-daily/reports/RUN_DATE.md`。
- 公开论文数据模块：`website/lib/paper-daily-RUN_DATE.ts`，并按计划发布日期接入 `reports`。
- 每篇入选论文的一至两幅原文方法图：`website/public/report-assets/RUN_DATE/`。
- 图片质量清单：`website/quality/figure-manifests/RUN_DATE.json`。
- 当期图片联系表：`website/quality/contact-sheets/RUN_DATE.png`。

上述 paper id、最终论文数量和图片数量必须一致。没有新候选或运行失败时遵循失败流程，不制造空的公开日报。

## 2. 检索与候选池门禁

1. 先确定计划发布日期与覆盖窗口：周一覆盖上周五至周日，周五覆盖本周一至周四。
2. 对窗口内每个自然日分别抓取 arXiv；读取 raw JSON、日志、`recommended_action` 与去重状态，记录没有公告批次的日期。
   历史重检必须使用官方 OAI `arXivRaw` 的 v1 version date 从零重建每日池，不能用最新修订日期或旧候选反推所属窗口。
3. 同步检查配置中的全部机构官方研究页、项目页、GitHub 和 Hugging Face。只有能定位到完整论文或技术报告、作者、机构、日期、方法与实验的官方材料才可补入。
4. 每个自然日先合并官方候选和 arXiv 候选，并按 arXiv id、规范化标题、作者及项目页去重，再保留最多 200 篇。逐日语义初筛完成后才合并窗口结果；不得设置窗口级 300 篇截断。存在 arXiv 版本时以 arXiv 为主记录。
5. 不得用旧批次、媒体报道、搜索摘要、产品新闻或演示视频填充候选池。

## 3. 两阶段筛选与全文门禁

### 第一阶段：全候选语义筛选

- 对每天最多 200 篇候选阅读标题、摘要、类别和检索原因，只记录 `must_fulltext_review`、`possible` 或 `reject` 及原因；标题/摘要阶段不生成论文质量分。
- 先执行领域硬过滤：医疗/手术、矿山、实验室自动化、液体处理、推荐系统、纯导航、具身问答导航、object navigation、traversability mapping、纯系统集成和硬件产品介绍原则上排除。
- 关键词、同义词和概念组只负责召回，命中数量不得累计为初筛分或质量分。
- `Code/ref` 中经原文核验的内容样例、HOST、tau0-VLA、RobotTTr、Masked Visual Actions 和经确认的跟踪公司高质量论文只作为召回与全文复核尺度的正向校准；不得获得固定质量加分或自动入选，当前候选仍须按自身方法与实验证据独立判断。
- 负向词也必须做语境确认：只允许明确的负向场景短语触发过滤，禁止把 `data mining`、`skill mining` 等方法语境当成矿山机器人论文；自动拒绝前至少核对标题与摘要。
- 经 PDF 首页或官方来源确认的跟踪公司论文可以获得有限的候选保护、全文复核和同等质量选择优先级；不得改变方法、实验、消融、复现质量分，也不得覆盖负向过滤。
- 每个自然日通常选择最多 20 篇进入第二阶段，不按关键词命中数量机械截断；候选稠密的单日可以贡献超过 5 篇最终论文。

### 第二阶段：正文复核

每篇最终入选论文都必须打开 arXiv HTML、PDF 或官方完整论文，至少核对：

- PDF 首页作者与机构，实验室或团队名仅在原文或项目页明确时记录。
- Introduction/Related Work 中的问题定义、最直接已有路线与新增贡献。
- Method 中的模型信息流、动作表示、训练或推理流程、损失函数及关键公式。
- Data/Training 中的数据规模、组成、来源、采集本体、训练阶段和关键设置。
- Experiments/Ablations 中的平台、任务或数据集、直接基线、试验次数、成功判据、关键结果、消融、泛化、失败案例和统计信息。
- Limitations/Conclusion 中作者明确说明的适用边界。

只能读取摘要的候选不得进入正式日报。没有真机实验的论文原则上降级或排除；预训练、世界模型评测或相邻领域通用方法只有在方法迁移价值显著、闭环或多基准证据充分、对照和消融可信时才可例外，并必须在本地审计中明确记录“无真机”及降权原因。

单个自然日不设 5 篇硬上限，整期总数按覆盖自然日数 × 5 封顶：周一窗口最多 15 篇，周五窗口最多 20 篇。不设最低数量；低质量、证据不足或与关注方向偏离时宁可少选。

## 4. 入选与排除审计

`RUN_DATE_scored.json` 和本地日报必须能够回答“为什么入选”和“为什么未入选”。至少记录：

- 候选总数、进入全文复核数、最终收录数和官方非 arXiv 补充数。
- 每篇入选论文的内部评分、阅读证据、机构证据和实验可信度 flags。
- 主要未入选候选及明确原因。原因优先使用：领域不相关、负向场景、纯导航/系统、重复或跨窗、无法获取全文、方法增量不足、实验或消融不足、对比不公平、只有演示证据、图片无法达到发布门槛。
- 不能用“综合质量一般”代替可核验的排除依据。

## 5. 内容证据与信息密度门禁

公开页面每篇论文必须包含：

1. 六张速览卡片：出发点、方法、模型结构、数据组成、实验内容和结论、相比 baseline 的改进点。
2. 三张编辑性小卡片：亮点、局限、可借鉴点。
3. 三段纵向详细正文：技术细节、实验和消融测试、可复现性。

逐篇检查以下要求：

- 六张速览卡片各自回答不同问题，不重复摘要或使用可互换的套话。
- “实验内容和结论”必须至少给出设置、直接对照、关键结果和证据边界；正文另行展开实验次数、成功判据、关键数值、消融与泛化条件。长框中只有笼统结论视为不合格。
- “相比 baseline 的改进点”必须说明最直接比较对象和新增机制；训练数据、算力或 backbone 不一致时说明混杂因素。
- “技术细节”按信息流讲清模型和优化过程；只有原文存在且有助理解时才列公式，公式与符号含义必须可读。
- “可复现性”连续写出原文确证的 backbone、网络或模块设置、输入输出、目标函数、关键超参数、训练硬件及代码/模型/数据状态。原文未披露时简洁说明，不用空泛占位填满版面。
- 每个精确数字、公式、结构细节和资源链接都能追溯到正文、表格、图注、附录或官方项目页；不得从柱状图大致估算后写成精确值。
- 作者自述的 “best”“human-level”“general” 只能以归因式表述，不改写成独立验证事实。
- 不做跨论文强行比较、宏观趋势判断或武断结论，不把 Prompt、评分、运行过程和生成免责声明写到公开页面。

## 6. 分类门禁

- 所有分类都按主要贡献判断，不因为某项技术在正文或附带实验中出现就打标签。
- 研究方向与训练优化各选一个主类别；创新模态和数据方法仅在它们是核心创新时标注。
- RGB 与 Language 不作为创新模态；Memory 的实现形式及长时/短时只进入详情属性。
- 机器人平台可组合；任务类型不进入数据库筛选器。
- “真机部署优化”必须以端侧延迟/吞吐、压缩、控制频率、传感器移除、资源占用、在线恢复或安全降级为主贡献并有直接实验。只有真机结果不得标注。
- 发布前逐篇做一次分类反查：标签必须能由方法或实验中的主贡献句直接解释。

## 7. 图片质量门禁

每篇论文使用一至两幅 Overview / Method / Architecture 原图，按以下顺序取图：arXiv HTML 独立 Figure、arXiv source 原始图片、官方论文或项目页原图、PDF 精确 figure bounding-box。

每张图必须：

- 与记录的 Figure 编号、图注和 source URL 对应。
- 完整包含全部 panel、框图分支、标签与 legend；无裁边、页眉、标题页、作者、页码和大段正文。
- 不是以 caption、空白、结果表或无关 rollout 照片为主体。
- 像素尺寸至少为 700×180；若原图无法达到门槛，换图或暂缓该论文，不用插值放大伪装清晰度。

发布前必须生成 contact sheet 并逐张视觉检查。manifest 至少记录 paper id、文件名、Figure 编号、直接来源 URL、来源类型、宽高、是否有页眉、框图是否完整和视觉检查结论。还必须把当期 manifest 加入 `website/tests/rendered-html.test.mjs` 的质量清单；只创建 JSON 而未纳入测试不算完成。

## 8. 网站与发布门禁

1. 按计划发布日期倒序接入 `website/lib/site-data.ts`，补跑时插入正确历史位置，不使用实际补跑日期或“补跑”字样。
2. 核对公开日报论文数、论文数据库条目、manifest paper id 与图片目录完全一致。
3. 核对 arXiv、项目页、GitHub、模型和数据链接；无法确认的链接直接省略。
4. 运行 `python -m pytest -q`、`npm run lint`、`npm test`、`npm run test:pages` 和 `git diff --check`。任何失败都必须先修复；不能跳过图片测试、静态导出测试或只运行构建。
5. 只提交本次运行相关文件，保留无关用户改动；不得提交本地评分数据、日志、完整本地日报和临时目录。周一的论文与公司改动必须进入同一个提交。提交前后检查 `origin/main`；只允许安全整合并普通 push，禁止 force-push、reset 或覆盖其他进程的提交。
6. 将最终提交推送到 `origin/main`，确认本次 `head_sha` 对应的 GitHub Pages workflow run 成功完成。旧 run、仅有 HTTP 200 或本地静态导出不能替代本次 Pages 部署确认。
7. 读取 `website/.openai/hosting.json` 并复用现有 Sites 项目。从同一根提交对应的精确 `website` 源码树生成 Sites 源提交和部署包，保存新版本、部署并轮询到 `succeeded`。
8. 发布后分别确认 GitHub Pages 和 ChatGPT Sites 的主页、当期日报、至少一条论文详情与代表性图片资源可访问。任一目标失败时明确说明各站点实际版本，不得声称已同步。

## 9. 完成回报

最终结果必须分别说明：覆盖窗口、候选/全文复核/最终收录数量、官方非 arXiv 补充数量、本地评分与日报路径、图片数量和 QA 状态、Python 与双目标网站测试、本地提交与 GitHub push、Pages workflow、Sites 版本、两个公开链接，以及任何失败或降级项。
